NexusOps · Target Architecture

Three planes: Planning, Deployment, Operations

Templatize a machine completely. Deploy it fully from that template. Then operate it from the UI — so touching the infrastructure by hand is rarely needed.

The problem

Three concerns, currently intercalated

The platform can already plan, deploy, and operate. What it cannot do is keep those three apart. Each capability is spread across modules that also do the other two:

ModuleHolds a definitionPerforms a changeReports live state
packagescatalog of packagesinstalls them—
deploymentscompose definitiondeploys itcontainer status
identitydesired users and groupsreplicates themdiscovers them back

The consequence is that no single object says “this is what a machine should be” — and so the platform can never answer “is this machine still what we said it should be?” Drift is not a missing feature; it is currently inexpressible.

The split

What each plane owns

Planning

What should exist

Pure desired state — nothing here touches infrastructure. The new aggregate root is the Machine Template: base image, disks and network, identity sets, packages, containers, services, monitoring expectations and access policy, composed into one versioned object. Templates are immutable once published; editing produces a new version, and every deployment records the exact version it realised.

machine templatespackage catalogcontainer definitions identity setsaccess profilesblueprintsparameter schemas

Deployment

Making it real, once

Owns the act of change — not the definition, not the ongoing state. Renders a template and its parameters into an execution plan, previews the diff against the target, executes it through the available executors, then registers the result into Operations carrying a link back to the template version that produced it.

Operations

What is actually there

Live machines and day-2 work: shell, files, logs, metrics, monitoring, lifecycle, nodes and storage. Its distinctive job is drift — observed state against the template version the machine came from. Every day-2 change offers two routes: an immediate ad-hoc action, or an edit to the template followed by a redeploy. The UI should make the second one attractive, because it is the one that keeps drift at zero.

The seam

ExecutionPlan makes the engine pluggable

One provider-neutral contract sits between Planning and every executor. Steps describe what should be true, never the commands that make it true — which is precisely what lets Terraform and Ansible arrive as additions rather than a rewrite.

The dashed return path is the whole point of the separation. Because the machine records which template version produced it, its observed state can be re-rendered and diffed — turning drift from an inexpressible question into a first-class status. 

// The contract every executor implements against
ExecutionPlan
  plan_id
  target:      TargetRef          // existing machine, or a spec for a new one
  source:      TemplateRef        // template id + version that produced this
  steps:       [ExecutionStep]

ExecutionStep
  step_id
  kind:        provision | identity | package | container
               | service | file | command | validate
  desired:     typed payload      // declarative, provider-neutral
  depends_on:  [step_id]
  executor:    ssh | ansible | terraform | proxmox
  idempotency_key
  rollback:    optional step

A capability matrix declares which executor realises which step kind, so a template can be deployed by whichever engine is available without the template changing. The same object also serves both UI audiences: a plain-language summary for the operator who wants “add a web server”, and the expanded step list with rendered commands, playbooks or HCL for the engineer who wants to see exactly what will run.

Delivery

Seven phases, each one deployable

Ordered because the dependencies are real, not for decoration. Phase 1 is the seam everything else hangs off; nothing after it can start until it lands. Every phase leaves the platform green — no long-lived branch.

01

The contract, behind existing behaviour

Introduce ExecutionPlan and a renderer. Wrap today's job runtime as SshExecutor. Route existing package, profile and action execution through plan → executor. No user-visible change.

02

Planning plane

planning

New backend/app/planning/. Introduce MachineTemplate composing existing catalogs by reference, plus versioning and validation. Catalogs move under Planning; their execution halves stay put for now.

03

Deployment plane

deployment

Move provisioning, deployments and profile-apply behind the plan pipeline. WorkflowRun becomes the single execution record for every kind of change. Add idempotency keys and preview/diff. Do the durable execution work here.

04

Operations plane

operations

Consolidate inventory, runtime state, monitoring and remote access. Add drift detection: render the observed plan from a machine, diff it against its template version.

05

AnsibleExecutor

The highest-value second executor. Identity, packages, services and files are exactly what Ansible is strongest at, and they are the steps most repeated across machines.

06

TerraformExecutor

Provisioning first, then whatever providers follow.

07

UI rebuild

Can start once the Phase 2 and 3 APIs are shaped, and proceed in parallel with 4–6 rather than waiting for them.

Prerequisite — schedule into Phase 3

Execution has to become durable first

The queue is in-process asyncio tasks with no persistence. A restart abandons in-flight work; startup reconciliation now closes those records out, but it marks them stale rather than resuming them.

Terraform applies and Ansible playbooks run for minutes, not seconds. Execution needs to survive a restart and move between processes before Phase 5 — which also lifts the single-instance ceiling that the in-process scheduler and rate limiter share. This is the one item that blocks the engine work, and it is much cheaper to do in Phase 3 than to discover in Phase 5.

Interface

Understandable, without being less technical

One pattern serves both audiences, and ExecutionPlan makes it natural: the same object, shown at two zoom levels.

Three top-level areas

Plan, Deploy, Operate. Everything belongs to exactly one. Anything that appears to belong to two is a signal the domain split is wrong at that point.

Progressive disclosure, not a simple mode and an advanced mode

Every action shows a plain-language summary by default, with the rendered plan, commands, playbook or HCL one click away. Two modes fork the product; two zoom levels do not.

Preview before every change

The diff is the trust-building surface — it is what lets an operator act without reaching for the terminal.

Drift is a status, not a report

Visible on every machine, with reconcile as the primary action.
